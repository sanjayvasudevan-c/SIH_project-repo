# GitHub-facing evidence pack — design

> Historical design record. The repo-native evidence narrative is retained; the in-app Evidence Center UI is intentionally not exposed in the current application.

Date: 2026-11-03 · Repo: `sanjayvasudevan-c/SIH_project-repo` · Branch: `claude/new-session-35imia`

## Intent and the why

An SIH evaluator who opens this repository currently lands on a README written for a developer who wants to run
the thing. Nothing on that first screen tells them the engineering is serious: that 183 integration tests run
against a real database, that the deadline engine was measured at 15,000 applications with zero duplicate
alerts, or that the yearly-rule-pack design is the part no competing team will have.

The audit (`docs/evidence/INITIAL_AUDIT.md`) found the code is in better shape than the presentation claims. So
this work is not about building capability. It is about making existing, already-measured capability legible to
someone who will spend about two minutes, will not clone the repo, will not log into the demo, and may be reading
on a phone.

The target reaction: *production-grade, feasible, and clearly ahead of the other submissions.*

## Goals

1. An evaluator understands the scope, maturity and standout ideas **from the repo landing page**, without
   clicking into a site or signing in.
2. Every figure shown is reproducible by a command in the repo, and the command is printed next to it.
3. Architecture (phases 0–8) versus what is actually built is stated plainly, with honest labels, so the ~40%
   implementation reads as deliberate scoping rather than something being hidden.
4. What stands out against the obvious alternatives (e-Office, a generic workflow engine, hard-coded rules) is
   argued, not asserted.

## Non-goals

- No new application features. The engine is tested and correct; this is presentation of existing behaviour.
- No in-app Evidence Center. That is the separate, larger plan in `docs/evidence/README.md`, deliberately not
  started here.
- No interactive web dashboard (see Approaches).
- No change to the SIH portal submission text. The recall discrepancy is noted, not acted on, pending a decision.

## Anti-goals — this fails even if it ships

- **Any number that cannot be reproduced.** A single figure an evaluator checks and finds wrong costs more than
  all six artifacts gain. This is the live risk: the submission text says 0.89 ML recall where the reproducible
  evaluation measures 0.863.
- **Looking marketed.** Government-domain evaluators discount decorated claims. Honest limitation sections are
  load-bearing, not throat-clearing.
- **Claiming production readiness.** Phase 8 hardening is absent; saying otherwise invites exactly the question
  that exposes it.

## Constraints

| Constraint | Consequence |
|---|---|
| GitHub does not execute JavaScript in Markdown | No interactive charts in the repo. Mermaid and SVG are rendered natively; both are used. |
| Evaluators may read on the GitHub mobile app | Wide tables and small-text SVG fail here. Charts must be legible at phone width. |
| GitHub renders Mermaid but not every diagram style | Flows use Mermaid; quantitative charts are committed SVG. |
| A live Vercel demo already exists | A second interactive site competes with it for attention rather than adding reach. |
| `api/scripts/load-test.ts` prints JSON to stdout and writes no file, and records no commit hash | The generator pipeline needs a small change to the script before charts can be generated from real output. |
| Audit findings that must not be contradicted | No tamper-proof-against-a-DBA claim, no exactly-once *external* delivery claim, all ML figures labelled synthetic. |

## Approaches

**A. GitHub Pages dashboard.** A built site with real interactive charts. Rejected. A live interactive app
already exists at Vercel, so this adds no capability an evaluator cannot already click; it needs a deliberate
click from the README that a skimming evaluator will not make; it introduces a build step that can silently
break; and the request was explicitly for GitHub rather than another application.

**B. Repo-native — chosen.** README section plus `docs/evidence/`, built from Mermaid diagrams, committed SVG
charts generated from real run output, badges, and tables. Visible on the first click, works in the mobile app
and offline, nothing to deploy. The trade-off is no interactivity — accepted, because the gap is readability in
two minutes, not interactivity. A static chart generated by a committed script from real run output is at least
as verifiable as an interactive one, since the generator is reviewable.

**C. Both.** Rejected: splits effort while the weak first click, the actual problem, stays weak.

Chosen: **B**.

## Design

### Cheaper path found

`demo-production/FEATURE_INVENTORY.md` already holds the architecture-versus-prototype comparison: a layer-by-layer
architecture table and ~37 features each with route, role, test steps, observable success and an honest status
(`Verified (API test …)`, partial, mocked, planned). It is strong material sitting in a folder about video
production, unlinked from the README, where no evaluator will find it.

So artifact 2 below is mostly **relocation, re-sourcing against the current commit, and linking** — not fresh
writing. Duplicating it would guarantee drift between two copies.

### Artifacts

| # | Path | Content | Source of truth |
|---|---|---|---|
| 1 | `README.md` (new section near the top) | Badges (tests, typecheck, build), a three-line "what this is", and a `verify it yourself` block of exact commands with their expected output | the commands themselves |
| 2 | `docs/evidence/ARCHITECTURE_VS_PROTOTYPE.md` | Phases 0–8 against what is built; per-module built / partial / planned; the ~40% figure explained as scope | `FEATURE_INVENTORY.md` (moved here), `INITIAL_AUDIT.md` |
| 3 | `docs/evidence/WORKFLOW.md` | Mermaid: case lifecycle state machine, assignment decision flow, escalation ladder (3/7/14 days), rule-pack publish with maker-checker and pinning | `workflow/transitions.ts`, `assignment/engine.ts`, `engine/cycle.ts`, `rules/versions.ts` |
| 4 | `docs/evidence/BENCHMARKS.md` + `docs/evidence/charts/*.svg` | Latency percentiles per screen, engine cycle duration, duplicate-alert prevention, dataset scale — as generated SVG | `docs/evidence/benchmark-results/*.json` from a real run |
| 5 | `docs/evidence/COMPARISON.md` | What a generic workflow/ticketing engine or a hard-coded rules implementation would have to add to do this job; what stands out here and why it matters to AICTE | the code, cited per claim |
| 6 | `docs/evidence/FEASIBILITY.md` | Zero licence cost, rollout phases (MVP → pilot → national), hosting (NIC/MeghRaj), what needs real AICTE validation, security roadmap | `3_abstract.txt`, `DECISIONS.md` |

### The generator pipeline

The rule is that no number is typed by hand. Three small producer changes, then one generator:

```
npm test -- --reporter=json      ─▶ docs/evidence/test-results/vitest.json      ─┐
npm run load:test -- --out <f>   ─▶ docs/evidence/benchmark-results/<commit>.json ┼─▶ scripts/evidence-charts.mjs
python -m training.evaluate      ─▶ formcheck/metrics.json                       ─┘          │
                                                                                            ▼
                                                                         docs/evidence/charts/*.svg
```

Producer changes (small, additive, no behaviour change):

- `api/scripts/load-test.ts`: add `--out <path>`; write the existing report object plus `commit`, `nodeVersion`,
  `pgVersion`, `timestamp`, `datasetSize`, `concurrency`. It already builds the object and prints it — this only
  persists it with provenance.
- `formcheck/training/evaluate.py`: also emit `metrics.json` beside `EVALUATION.md`, same numbers.
- `scripts/evidence-charts.mjs`: read those JSON files, write SVG. Hand-rolled SVG strings, no chart library —
  the output must be small, diffable, legible at phone width, and readable in both GitHub themes.

Charts use `currentColor` and theme-neutral accents so they are legible in light and dark mode. Every chart
embeds its commit hash and run date as a caption, so a stale chart is visibly stale.

### Decisions I am making, flagged as mine

1. **Measured figures only.** ML recall is published as **0.863** with precision 0.975 and a 2.2% false-alarm
   rate. The submission text's 0.89 / 2.9% is not used anywhere in the repo. Reconciling the portal text stays
   the user's separate call.
2. **`FEATURE_INVENTORY.md` moves** to `docs/evidence/` and the old path is not kept as a copy. One source.
3. **Benchmarks are re-run on the current commit** rather than citing the 26 Oct figures, so the artifact and the
   code agree. Expected ~7 minutes; if a figure comes out materially worse than 26 Oct, it is published as
   measured and the regression investigated, not quietly dropped.
4. **Limitations sit inline**, under the number they qualify, not in a trailing section an evaluator skips.
5. **No lint tool is introduced** here. The audit found none configured; adding one is its own change and would
   churn files unrelated to this work.
6. **The comparison argues from design properties, never from claims about another product's features.** Saying
   "e-Office cannot do X" would be an unsourced assertion about a real government system — exactly the kind of
   checkable-and-wrong claim the anti-goals rule out. Instead: state the property (a filed case keeps the rules
   it was filed under when the handbook changes mid-cycle), show where this repo implements it, and let the
   reader judge what a generic workflow tool would need to add. Where a named system is mentioned at all, it is
   as a category, without feature claims.

### What is left to the builder

- Exact chart forms (bar, dot plot, small multiples) per metric, subject to phone-width legibility.
- Mermaid diagram granularity — enough to show the mechanism, few enough boxes to read on a phone. The slide-3
  architecture diagram is known to be too dense on a projector; do not repeat that mistake here.
- Badge source. Static shields with values generated from real output are acceptable and honest while there is no
  CI; a live CI badge is better and arrives with the separate CI work.
- README section length. It must not push the existing quick-start below the fold.

## Risks

| Risk | Handling |
|---|---|
| The re-run benchmark is worse than the 26 Oct run | Publish as measured; investigate. Suppressing it would breach the anti-goal. |
| Six documents nobody reads | The README section is the product; the documents are depth behind it. If only the README section gets read, the work still lands. |
| Mermaid renders differently than expected | Verify each diagram renders on GitHub before closing the work. |
| Moving `FEATURE_INVENTORY.md` breaks a link | Grep for references before moving. |
| `npm test -- --reporter=json` may not forward the flag through two npm workspace layers | Check first; fall back to running `npx vitest run --reporter=json` inside `api/`, or add a dedicated `test:json` script. |
| `load:test` resets the demo database at both ends | Expected and documented in `docs/LOAD_TEST.md`. Only run it against a local or disposable database, never the hosted Neon one. |
